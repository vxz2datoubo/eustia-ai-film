# 场景与空间设定库

> 本文件维护固定场景的性质、材质、功能、氛围、固定结构、道具、光源、局部动线和场景资产关系。空间拓扑、相邻关系、入口、方向、桥路高低和真实可达路线的唯一权威为[00_项目地图文件](00_项目地图文件.md)。
> 场景 / Camera Anchor / View / Media Asset / Relation 的机器身份、命名、方位与resolver规则统一服从 `../10_运行时/scene_asset_identity_schema.yaml`。
> 场景提示词必须先写“整体风格总览”，再写具体区域、方向、结构、物件、光线、功能和人物动线。

> GitHub-first reconcile：本文件保留源文件的场景知识；任何方向、拓扑、入口与相邻关系如与地图冲突，地图优先。2026-08-14 用户确认正式世界方向为“北=钟楼/关所侧，南=绯灯街/蔷薇酒馆侧”；正式场景图的人类可读名称使用中文，机器身份使用 ASCII opaque ID。

# 1. 世界空间总则

- 架空中世纪晚期空中都市底层
- 中世纪手工时代材质
- 底层城市被悬崖、岩壁和高墙包围
- 默认不出现现代物品、现代道路、电灯和开放天空
- 建筑比例、道路连通、楼层高低和相邻关系必须稳定
- 场景是社会机制和权力结构，不只是装饰背景

# 2. 总拓扑（局部摘要；地图唯一权威）

南 → 北：

```yaml
route:
  - 莉莉会所
  - 绯灯街S形生活商业街
  - 蔷薇酒馆
  - 主街道
  - 横向高架石桥
  - 市集与布道施粥广场
  - 教堂钟楼
  - 钟楼后方 / 北侧的关所底层入口
  - 关所内部唯一受控上行通道
```

# 3. 莉莉会所

## 性质

旧欧洲中世纪晚期风格为主体的底层灰色歌舞娱乐场所。不是现代夜店，不是贵族宫廷。可少量加入中式屏风、帘子、花格、流苏和红木色细节，但不得改变欧洲中世纪主体。

## 固定空间

```yaml
entrance:
  reception: left
  screen: near_entrance
ground_floor:
  booths: multiple
  dance_area: small
stair:
  position: left_of_center
second_floor:
  office_overlook: true
```

## 功能

- 歌舞、陪酒与灰色消费
- 金锁上纳金、信息流和雇佣节点
- 不能只作为华丽背景

# 4. 绯灯街

- 位于当前主空间链南侧。
- S形石板街
- 商铺、住户、娼馆、酒馆、医疗、仓储和装卸混合
- 房屋密集但保留可行走巷道
- 体面、暧昧、贫穷、旧化和生活感并存
- 社会功能详见[AI电影项目记忆](../02_AI电影项目记忆/AI电影项目记忆.md)第8章；拓扑与方向详见地图

# 5. 蔷薇酒馆

- 位于绯灯街北侧出口 / 主街南侧过渡节点。
- 经营者：梅尔特
- 中文招牌：蔷薇酒馆
- 是生活区、信息流和主街出口之间的过渡节点

# 6. 主街与横向高架石桥

```yaml
bridge:
  elevation: upper
  orientation: east_west
  relation: OVER main_street
main_street:
  elevation: lower
  orientation: north_south
  relation: UNDER bridge
intersection:
  same_level_crossroad: forbidden
  bridge_deck_continuous: true
  street_occluded_under_bridge: true
```

- 主街从南侧蔷薇酒馆 / 绯灯街方向通往北侧市集 / 钟楼方向。
- 桥下仍为仓储、推车、运输和通行。
- 生成俯视图时必须明确桥上路下。

# 7. 市集与布道施粥广场

- 位于高架石桥北侧、教堂钟楼南侧。
- 两侧摊位和堆货
- 中央通道兼具通行、集会和布道
- 木桌、推车、木碗、小圣像、麻袋、木箱和棚布
- 布道与施粥同时发生
- 群众行为来自生存和信仰，不是纯礼仪摆拍

# 8. 教堂钟楼与关所（地图裁决已应用）

- 教堂钟楼位于市集广场**北端**，前方 / 南侧有长石阶；圣女在塔前或塔基区域布道。
- 关所位于钟楼后方 / **北侧**，其底层入口属于牢狱底层；两者制度上邻接，但不是同一建筑或同一上行楼梯。
- 教会发布和上层控制可在同一制度空间中呈现，但镜头空间连续性必须服从地图。

# 9. 关所内部的唯一上层通道（地图裁决已应用）

- 关所底层入口位于钟楼后方 / 北侧；进入关所内部后才开始上行。
- 封闭式运输入口
- 检查岗
- 厚重石门
- 封闭拱口
- 四方回旋楼梯
- 栏杆与集散平台
- 是牢狱通往中层的唯一受控合法主通道；教堂钟楼不承担该交通功能

# 10. 顶视场景接口

> 顶视图方向统一按 `scene_asset_identity_schema.yaml` 解释。摄影机本身向下，正式方向字段记录“画面上方对应哪个世界绝对方位”。

```yaml
scene:
  scene_id:
  display_name_zh:
  source_resolution:
  coordinate_system: normalized_top_left
camera_anchor:
  camera_anchor_id:
  world_position_relation:
view:
  view_id:
  view_class: top_orthographic | top_oblique
  screen_top_cardinal: N | S | E | W
  projection: orthographic | perspective_oblique
  pitch_deg: 90
  roll_deg: 0
layers:
objects:
relations:
paths:
excluded_regions:
render:
negative_constraints:
invariants:
```

例如：

- `screen_top_cardinal: N` = 中文“北朝上顶视图”。
- `screen_top_cardinal: S` = 中文“南朝上顶视图”。
- 同一场景可以有北朝上与南朝上等不同 View，不得靠旧文件名或未经核验的旋转图自动替代。

## 11.1 场景资产调用语义

- 用户说“桥南边往北看”时，应解析为：`scene=高架石桥` + `camera_anchor=桥南侧某机位` + `facing_cardinal=N`，而不是只搜索“北向图”。
- 如果同一场景有两个不同机位都朝北，必须先由人物位置、镜头调度、用户指定或地图关系确定 Camera Anchor，再选择 View。
- 用户说“反打”时，不允许简单把 N 改成 S；必须查询显式 Relation，判断它是同机位180°、跨机位互看还是导演剪辑关系。
- 中文显示名可以调整以便用户理解；机器 ID 一旦分配即保持稳定，避免中文改名导致引用链断裂。
- 二进制媒体默认使用 ASCII storage filename；中文正式名、别名、用途、方向和机位信息保存在 GitHub metadata。
