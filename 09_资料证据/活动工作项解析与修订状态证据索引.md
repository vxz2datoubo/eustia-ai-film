# 活动工作项解析与修订状态证据索引

> 本文件只承担外部专业知识、标准、论文与工程模式证据职责。它不定义项目当前 work item，不覆盖 `PROJECT_INDEX.yaml`、当前剧本、连续性、地图、资产或 `AI电影系统.md`。

# 1. 当前项目问题

2026-08-29 出现真实 P0 路由失败：用户说“重新导演上次那30秒”，实际指当前屋顶围巾滑绳 work item，但旧连续性仍把较早的攀爬/木窗/菲奥奈/登顶段写成当前30秒。由于缺少 Active Work Item Resolution Gate，错误 work item 在 Director Feature Compiler 之前没有被发现，后续导演、学习召回和提示词编译均在错误对象上正常运行。

本研究寻找能够解决以下问题的成熟专业机制：

- work item identity / referent resolution
- multi-turn ellipsis and co-reference
- revision event trace vs current snapshot
- checkpoint / snapshot compaction
- provenance / revision lineage
- optimistic concurrency / idempotency
- state transition validation
- one revision relating to multiple project objects
- cross-agent / cross-window structured context and tracing

# 2. T1 标准与官方工程资料

## EVID-AWIR-001｜W3C PROV-DM

Source: W3C Recommendation / PROV Data Model
URL: https://www.w3.org/TR/prov-dm/
Evidence tier: T1 standard

Relevant mechanisms:

- PROV-DM separates Entity, Activity and Agent and explicitly models derivation.
- `Revision` is a subtype of derivation: a revised entity derives from a preceding entity while retaining substantial content.
- provenance can be bundled and can describe provenance of provenance.
- primary source, derivation, attribution and responsibility are distinct relations.

Project mapping:

- revision checkpoint must record `parent_revision` / `source_ref`, not only the final prompt text.
- Issue comment is evidence trace; continuity snapshot is a derived current-state representation.
- CANONICAL_CHECKPOINT receipt should link the snapshot back to the source revision/checkpoint.

Boundary:

- PROV-DM does not tell us which creative constraint is authoritative. Project authority order still comes from `PROJECT_INDEX.yaml` / `source_authority.yaml`.

## EVID-AWIR-002｜Microsoft Azure Event Sourcing Pattern

Source: Microsoft Azure Architecture Center
URL: https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing
Evidence tier: T1 official engineering guidance

Relevant mechanisms:

- append-only event streams preserve the sequence and intent of changes.
- current state can be reconstructed by replaying events.
- snapshots reduce rehydration cost but remain an optimization, not the source-of-truth event history.
- optimistic concurrency rejects stale appends and forces re-read/re-evaluation.
- event sourcing is powerful but adds complexity and should be used only where audit/history benefits justify it.

Project mapping:

- Issue/Micro Capture revision trace = append-only event stream.
- `continuity#ACTIVE_WORK_ITEM_STATE` = materialized snapshot for fast continuation reads.
- FETCH → EDIT → COMMIT → FETCH VERIFY = project-level optimistic write discipline.
- snapshot must never replace Git history / revision evidence.

Boundary:

- do not migrate the entire project to generic event sourcing. Apply the pattern only to revision/work-item state where history and reconstruction are already natural requirements.

## EVID-AWIR-003｜Microsoft Azure CQRS Pattern

Source: Microsoft Azure Architecture Center
URL: https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs
Evidence tier: T1 official engineering guidance

Relevant mechanisms:

- event history can be the write model while a denormalized materialized view serves efficient reads.
- read models may lag and therefore require explicit consistency handling.
- snapshots/read projections optimize retrieval but must be rebuildable from authoritative history.

Project mapping:

- revision evidence is the write/history side.
- compact active work item state is the read projection used by director routing.
- a stale projection must be detected before directing, not silently trusted.

## EVID-AWIR-004｜Microsoft Minimize Coordination / Idempotency / Optimistic Concurrency

Source: Microsoft Azure Architecture Center design principles
URL: https://learn.microsoft.com/en-us/azure/architecture/guide/design-principles/minimize-coordination
Evidence tier: T1 official engineering guidance

Relevant mechanisms:

- design operations to be idempotent when retries are possible.
- prefer optimistic concurrency when practical.
- partition state and coordination to the smallest relevant object.

Project mapping:

- checkpoint receipts require stable revision IDs so retries do not duplicate state changes.
- only the active source Issue should be probed for new checkpoints, not the entire repository.
- work item ID is the partition key for revision reconciliation.

## EVID-AWIR-005｜CloudEvents 1.0

Source: CNCF CloudEvents specification
URL: https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md
Evidence tier: T1 open standard

Relevant mechanisms:

- required event identity separates `id`, `source`, `type` and version.
- `source + id` uniquely identifies a distinct event and supports duplicate detection.
- `subject` identifies the object the event concerns without overloading the event payload.

Project mapping:

- revision event envelope should separate `revision_id`, `source_ref`, `event_type`, `work_item_id` instead of encoding everything into one free-text comment title.
- checkpoint retry can be idempotent if the same revision/source pair is recognized as already applied.

Boundary:

- we borrow the identity separation mechanism, not the wire protocol or event transport stack.

## EVID-AWIR-006｜W3C SCXML

Source: W3C Recommendation / State Chart XML 1.0
URL: https://www.w3.org/TR/scxml/
Evidence tier: T1 standard

Relevant mechanisms:

- explicit states, transitions and event-driven state-machine semantics.
- invalid or undefined transitions are a first-class design problem rather than informal prose.

Project mapping:

- work item lifecycle uses bounded states such as `UNRESOLVED → RESOLVED_UNVERIFIED → RESOLVED_VERIFIED → ACTIVE_REVISION → CHECKPOINTED → CLOSED`.
- downstream directing cannot treat `UNRESOLVED` as if it were `ACTIVE_REVISION`.

Boundary:

- do not import SCXML syntax or a full statechart engine; only use explicit transition semantics.

## EVID-AWIR-007｜OCEL 2.0 Object-Centric Event Logs

Source: OCEL standard / Process and Data Science community
URLs:
- https://www.ocel-standard.org/
- https://www.ocel-standard.org/specification/overview/
Evidence tier: T1/T2 standard + research community

Relevant mechanisms:

- every object has stable identity and type.
- one event may relate to multiple objects through qualified event-to-object relations.
- objects may also have object-to-object relations.
- forcing complex real processes into a single naive “case notion” can duplicate, lose or mis-associate events.

Project mapping:

- a single revision may simultaneously concern WorkItem, Shot, Character, Scene, Asset, ModelVersion and Evidence.
- work item remains the primary revision partition, but related objects should be explicitly linked with role qualifiers rather than concatenated into a fuzzy text key.
- this reduces alias collision such as two different “凯姆30秒” segments.

Boundary:

- we do not adopt OCEL storage as a second database. The project keeps GitHub canonical and uses the object-centric model only to shape identifiers and relation fields.

# 3. T2 同行评审 / 学术机制

## EVID-AWIR-008｜GECOR: Ellipsis and Co-reference Resolution for Task-Oriented Dialogue

Source: ACL Anthology / EMNLP-IJCNLP 2019
URL: https://aclanthology.org/D19-1462/
Evidence tier: T2 peer-reviewed

Relevant mechanisms:

- ellipsis and co-reference are ubiquitous in multi-turn task dialogue.
- one viable framing is to reconstruct a pragmatically complete user utterance from the dialogue context before downstream task execution.

Project mapping:

- “继续”“那30秒”“刚才那个镜头” should be treated as incomplete task references requiring referent reconstruction before Director Feature Compiler.
- downstream intent classification must not be asked to infer task identity from an unresolved ellipsis.

Boundary:

- the project does not need to reproduce the GECOR neural architecture. We adopt only the problem decomposition: reference resolution first, task execution second.

## EVID-AWIR-009｜Reference Resolution in Situated Dialogue

Source: ACL Anthology / SIGDIAL 2016
URL: https://aclanthology.org/W16-3642/
Evidence tier: T2 peer-reviewed

Relevant mechanism:

- reference resolution becomes a grounded task when multiple candidate objects exist in a situated environment.

Project mapping:

- “那个30秒” is not resolved by lexical similarity alone; candidate work-item identity must be grounded in structured project context.

## EVID-AWIR-010｜Reasoning over Object Descriptions Improves Coreference Resolution in Task-Based Dialogue

Source: LREC 2026 / ACL Anthology
URL: https://aclanthology.org/2026.lrec-1.224/
Evidence tier: T2 peer-reviewed, recent

Relevant mechanism:

- reference resolution improves when the system reasons over structured object descriptions rather than only surface mentions.

Project mapping:

- each work item should expose a compact identity description: ID, status, source issue, story scope, locked/revoked constraints and a few structured aliases/relations.
- the resolver should use that structure to distinguish two semantically similar “凯姆30秒” tasks.

Boundary:

- this paper concerns task-based dialogue/object references, not film production specifically. Use as candidate architecture evidence only.

## EVID-AWIR-011｜Advanced Case Notions in Object-Centric Process Mining

Source: International Conference on Process Mining 2025 / Springer LNBIP
URL: https://link.springer.com/chapter/10.1007/978-3-031-82225-4_30
Evidence tier: T2 peer-reviewed

Relevant mechanisms:

- real processes involve multiple related objects; choosing the wrong case notion can create lost, duplicated or incorrectly related events.

Project mapping:

- `work_item_id` is the revision partition, but revision relations to shot/asset/model/evidence must remain explicit.
- similarity-based “all 凯姆30秒 belong to one case” is structurally unsafe.

# 5. 形成的候选架构知识

## 5.1 Event Trace + Materialized Snapshot

```text
Revision Events / Issue evidence
        ↓
Constraint Ledger replay
        ↓
ACTIVE_WORK_ITEM_STATE snapshot
        ↓
fast director reads
```

The snapshot is an optimization and current-state projection. The revision trace remains necessary for audit, Final-Delta and conflict reconstruction.

## 5.2 Resolve Before Compile

```text
User utterance
→ continuation / ellipsis detection
→ work-item referent resolution
→ freshness reconcile
→ canonical targeted reads
→ Director Feature Compiler
```

This ordering is the highest-impact fix for the 2026-08-29 failure.

## 5.3 Stable Identity > Similar Text

Work item identity must not be inferred from:

- same character
- same duration
- same scene family
- most recently modified file
- highest semantic similarity

Those are retrieval clues, not identity authority.

## 5.4 Qualified Multi-Object Relations

A revision can carry relations such as:

```yaml
related_objects:
  - {type: work_item, id: KAIM-SCARF-CLOTHESLINE-TRAVERSE, role: primary_case}
  - {type: character, id: CHARACTER-EUSTIA-KAIM, role: performer}
  - {type: model, id: C-DANCE-2.5, role: generated_with}
  - {type: evidence, id: issue19-comment-5454103847, role: observed_output_feedback}
```

Do not encode all relations in the work-item name.

## 5.5 Fail Closed on Unresolved Reference

If two materially plausible work items remain, ask one minimal discriminating question. A short question is cheaper than producing a complete wrong 30-second director plan.

# 6. K0-K3 映射

## K0｜用户明确知道并已经说出的

- 当前 work item 可以跨多个聊天回合持续。
- “省略不等于撤销”。
- 用户希望系统自动管理 Checkpoint / Final-Delta / GitHub 写回。
- 当前屋顶滑绳已经取代旧攀爬30秒成为活动制作项。

## K1｜用户已经在实际工作中依赖、但未必用工程术语表达的

- work item 需要稳定身份，不应由“凯姆+30秒”这种表面字符串定义。
- 当前状态应该能快速恢复，不应每轮全文重放所有聊天。
- 修订历史仍要保存，因为最终要分析哪一步真正有效。
- 系统必须能在不同窗口继续同一条 revision series。

## K2｜邻接专业知识

- Event Sourcing / Materialized View
- optimistic concurrency
- idempotency
- provenance / revision lineage
- state machine / transition validation
- object-centric event data
- dialogue ellipsis/coreference resolution
- run context / traces / handoff packets

这些都可以解释后用于本项目，但先保持 candidate。

## K3｜用户很难主动想到、但会在大型长期制作中踩中的问题

- 两个不同 work item 使用同一角色、同一时长、同一关键词而发生 alias collision。
- source Issue 写成功但 continuity snapshot 写失败，产生 projection lag。
- 同一 revision 同时改镜头、资产、模型和声音，单一 case key 造成错误归并。
- Checkpoint 重试导致同一 Delta 被重复应用。
- work item 被拆成两个或两个 work item 合并时，旧 ID 与新 ID 的关系不明确。
- 跨窗口 handoff 只传自然语言摘要，没有 machine identity receipt。
- 旧 work item 重新激活时错误覆盖当前 active pointer。
- source Issue 不可访问时系统把 stale snapshot 当 fresh。

K3 默认先进入 targeted regression / UNKNOWN，不直接变成稳定规则。

# 7. 当前建议

采用 `ACTIVE-WORK-ITEM-RESOLUTION-001`，但保持项目现有 GitHub-first 结构：

- 不引入新的数据库或外部 workflow 产品作为生产依赖。
- 不把 Issue 变成 screenplay/continuity authority。
- 只在 continuity 中增加 compact active snapshot。
- Issue/comments 继续承担事件轨迹与生产证据。
- resolver 在 Director Feature Compiler 前 fail closed。
- 输出前再次做 work-item identity gate。
- 真实跨窗口生产成功后再把该机制从 candidate 晋级。
