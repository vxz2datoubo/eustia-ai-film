# 视觉资产登记库

> 本文件是角色、场景、服装、白模、深度图、视频参考等**逻辑媒体资产身份、状态、职责、默认指针与连续性绑定**的唯一可写文字登记库。媒体本体继续保存在 ChatGPT Library / Project 可访问位置。
> 正式场景媒体的 Scene / Camera Anchor / View / Media Asset / Media Version / Relation 身份结构统一服从 `../10_运行时/scene_asset_identity_schema.yaml`；场景 Asset 的 current Media Version、版本历史、content hash 与 locator 由 `../10_运行时/scene_media_resolver_manifest.yaml` 唯一维护。本文件不复制第二套版本清单。

## 1. 强制入库语义

用户说：

- “登记资产”
- “登记进资产”
- “加入资产库”
- “录入资产”
- “设为正式资产”

默认就是正式 `active` 入库请求。除非用户明确说 `candidate / temporary / pending_review`。

正式完成必须执行：

```text
识别资产身份与职责
→ 检查同类资产 / 默认指针 / 连续性
→ 对场景资产解析 Scene → Camera Anchor → View → Media Asset → Media Version → Relation
→ 写本登记库中的逻辑Asset / 默认职责
→ 写resolver manifest中的current version / hash / locator
→ 必要时同步地图 / 场景 / 连续性
→ COMMIT serially
→ FETCH VERIFY
```

Memory、口头确认或“准备好条目”都不能替代正式入库。

## 2. 状态

- `active`：正式逻辑资产；在自己的职责通道中可默认调用。
- `alternate`：合法备选。
- `pending_review`：历史存在但未重新核验，不得默认调用。
- `missing`：登记存在但媒体缺失。
- `active_text_missing_visual`：文字空间节点正式，但独立视觉母图缺失。
- `temporary`：只服务当前镜头，不进入长期身份默认。
- `deprecated`：禁止默认调用。

场景媒体实际像素版本的生命周期不在这里维护，统一由 `scene_media_resolver_manifest.yaml` 的 `pending_verification / current / superseded / archived / missing_binary / rejected` 管理。

## 3. 调用优先级

```text
用户本次明确指定
→ 当前镜头连续性绑定
→ 当前 View 的正式默认 Media Asset
→ resolver manifest 中该 Asset 的 current Media Version
→ 当前版本的 verified locator
→ 合法备选 / 光照时间变体
→ 明确报告缺失
```

## 3.1 正式场景资产身份与命名规则｜2026-08-14 用户确认

- 世界绝对方向服从 canonical 地图：**北 = 教堂钟楼 / 关所侧；南 = 绯灯街 / 蔷薇酒馆侧**。
- 用户层和正式显示名统一使用中文；用户无需记英文或机器 ID。
- 机器层使用 ASCII opaque ID，并且**不在 ID 中编码地点、方向、左右、正反打等可变化语义**：
  - Scene：`EUS-SCN-######`
  - Camera Anchor：`EUS-CAM-######`
  - View：`EUS-VIEW-######`
  - Media Asset：`EUS-AST-######`，表示长期稳定的逻辑媒体职责槽
  - Media Version：`EUS-VER-######`，表示不可变的实际像素修订
  - Relation：`EUS-REL-######`
- 中文显示名可因更准确的场景理解而修改；opaque machine ID 一旦分配不随改名变化。
- 二进制媒体的推荐 storage filename 使用 ASCII **Media Version ID**，例如 `EUS-VER-000083.png`；中文正式名、别名、机位、方向与用途保存在 GitHub metadata。已有中文文件名可以继续作为 locator，不把文件名当 canonical identity。
- 普通 View 正式方向只使用：**朝北 / 朝南 / 朝东 / 朝西**。方向表示摄影机水平朝向。
- 顶视 View 使用：**北朝上 / 南朝上 / 东朝上 / 西朝上**。方向表示画面顶部世界方位；摄影机本身仍向下。
- “北侧机位”与“朝北视图”不是同一个概念。前者是 Camera Anchor 的世界位置，后者是 View 的摄影机方向。
- 同一场景可以有多个不同 Camera Anchor 都朝同一方向。导演必须先确定机位，再确定 View。
- “正打 / 反打 / 左视 / 右视”不再作为正式主方向名，也不能靠名字自动推断。
- 场景资产的正反打、同机位180°、跨机位互看等关系必须通过 Relation 显式绑定。
- 场景母图反复修改时，**默认保留 Asset ID，不通过删除旧文件或同名覆盖维持身份**；真正变化的像素进入 Media Version 层。
- 完整 schema、字段、resolver、迁移事务与验收规则见 `scene_asset_identity_schema.yaml` 与 `scene_media_resolver_manifest.yaml`，本文件不复制第二套定义。

## 3.2 中文正式名格式

```text
Scene：{场景名}
Camera Anchor：{场景名}·{绝对位置描述}·机位{NN}
Perspective View：{场景名}·{机位名}·朝{北|南|东|西}{视图职责}
Top View：{场景名}·{北|南|东|西}朝上{顶视职责}
Media Asset：{View正式名}·{媒体角色/时间/天气/光照职责}
Media Version：{Media Asset正式名}·修订{NN}
```

示例：

```text
高架石桥·南侧桥头·机位01
高架石桥·南侧桥头·机位01·朝北主视图
高架石桥·南侧桥头·机位01·朝北主视图·阴天日间彩色母图
高架石桥·南侧桥头·机位01·朝北主视图·阴天日间彩色母图·修订02
高架石桥·北朝上正交顶视图
```

精确斜角不创造“东北”等新的主方向标签；需要时在 View metadata 记录 `yaw_offset_deg`。

## 3.3 Relation 绑定

正式 View 之间至少支持：

- `same_anchor_180`：同一 Camera Anchor 原地180°转向。
- `same_anchor_90`：同一 Camera Anchor 的侧向视图。
- `reciprocal_cross_anchor`：两个不同 Camera Anchor 之间的互看 / 对位。
- `editorial_shot_reverse_shot`：导演或剪辑层明确指定的正反打关系；不要求物理上严格同机位180°。
- `top_view_orientation_pair`：同一场景不同“朝上方向”的顶视配对。

重要：一个朝北、一个朝南**不自动等于正反打**。必须确认 Camera Anchor、轴线、视线、空间可达和 Relation。

## 3.4 Asset / Media Version / Locator 分层

正式场景媒体不再把 Asset ID、File ID、文件名和像素版本混成一个对象。

```yaml
logical_asset:
  asset_id:
  view_id:
  display_name_zh:
  media_role:
  lighting_state:
  weather_state:
  time_state:
  status:

resolver_manifest:
  current_version_id:
  versions:
    - version_id:
      revision_no:
      content_hash:
      pixel_verified:
      lifecycle_status:
      locators:
```

- `asset_id`：稳定逻辑身份，表示“这个 View 下承担这个正式媒体职责的资产槽”。
- `version_id`：某一次实际像素内容的不可变身份。
- `source_file_id / library title / local path / external URI` 等只是 locator，可以增加、失效或迁移，不改变 Asset 或 Version 身份。
- 一个 Asset 可以有多次像素修订，但普通导演默认只解析 `current_version_id`。
- 已生成镜头、回归案例或需要严格复现的任务可以额外锁定 `media_version_id`，不随 current 更新。
- 如果当前会话无法从某个 locator 打开正式像素，系统应尝试同一 Version 的其他 verified locator；全部失败时只能报告“正式身份已找到但像素不可用”，不得拿候选图冒充。

## 3.5 修改、重传、变体、新机位的自动分类

用户重新发图时，系统先判断它属于哪一类：

1. **同像素重传**：content hash 相同，Asset 相同 → 不建新 Version，只增加/刷新 locator。
2. **同 Asset 新修订**：像素改变，但 Scene、Camera Anchor、View、media_role、时间/天气/光照职责都没变 → 建新 Media Version；核验后切 current，旧版标 `superseded`。
3. **并列 Variant**：有意改变时间、天气、光照或媒体职责，并且两版都需要长期保留 → 同一 View 下建立不同 Asset，各自有自己的版本链。
4. **新机位 / 新 View**：摄影机实际位置、朝向职责、顶视朝上方向或 View 职责实质变化 → 建新的 Camera Anchor / View / Asset，不得伪装成旧 Asset 的新版。

普通替换**不物理删除旧版本**。旧版本先进入 `superseded`；只有用户明确要求删除，并通过“非current、无活动引用、无回归/证据用途、可恢复性”检查后才允许物理删除。若当前存储工具不提供删除能力，只能更新生命周期状态，不能声称文件已经物理删除。

# 8. 场景资产身份与版本迁移事务

- `秽翼AI电影资产总表_CURRENT_v5.xlsx` 保留在 Library 作为 2026-08-11 迁移前快照和对账证据。
- 本文件后续统一保存正式**逻辑 Asset**状态、职责、中文名称、View / Relation 绑定和默认指针；`scene_media_resolver_manifest.yaml` 唯一保存 Scene Asset 的 current Media Version、版本历史、content hash 与 locators。
- 旧 `SCN-*` 场景 registry key 不作为长期兼容层。用户按计划逐张重新上传或提供可打开正式图后，按 `scene_asset_identity_schema.yaml` 执行：

```text
FETCH所有活动引用 + resolver manifest
→ 实际打开正式像素
→ 与用户核对地点 / Camera Anchor / 朝向 / 地标 / Relation
→ 分配新的 opaque Scene / Camera Anchor / View / Asset / Relation ID
→ 为实际像素分配 Media Version ID
→ 记录 content hash / pixel_verified / verified locators
→ 设置 Asset → current_version_id
→ 写中文正式名与metadata
→ 全仓搜索旧key/旧名称/旧方向引用
→ 串行替换全部活动canonical引用
→ FETCH AGAIN
→ 验证新ID、current version、locator与Relation全部可解析
→ 验证旧key在活动canonical引用数 = 0
→ 关闭事务
```

- 事务完成后旧身份只存在于 Git 历史；**不建立永久 old→new mapping**。
- 以后同一 Asset 再次修改，只新增 Media Version 并移动 `current_version_id`，不重新迁移 Scene / Camera Anchor / View / Asset / Relation。
- 如果只是同一像素重新上传，则只补 locator，不制造假版本。
- 如果多文件串行迁移或版本切换中途失败，不得声称完成；在连续性记录 blocked transaction，并在下一项目回合优先恢复。
- 剧情工作母本、纯原作母本等非视觉资源不在本文件重复登记，转由剧本 / 证据体系维护。
