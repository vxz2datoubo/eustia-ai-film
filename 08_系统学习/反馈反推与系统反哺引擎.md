# 反馈反推与系统反哺引擎

> 本文件负责把用户反馈与真实生成结果转成可验证的学习对象，并路由到唯一主文件。它不保存第二份规则副本。

# 1. 固定闭环

```text
先修当前结果
→ 比较修改前后
→ 判断真正解决了什么问题
→ 推测真实意图与价值排序
→ 区分临时要求和稳定规律
→ 做反事实与替代解释
→ 定义适用条件、边界、反例和失效条件
→ 标记成熟度
→ 写回唯一目标文件
→ 回读验证
→ 必要时增加回归案例
```

# 2. 学习成熟度

```text
candidate
→ scene_verified
→ project_verified
→ general_stable
```

旁路状态：

- `conflicted`：存在相反有效经验，按边界路由，不静默覆盖。
- `needs_revalidation`：模型、工具或版本变化使旧经验可能过期。
- `deprecated`：已被替代或证伪。

一次成功不能自动成为通用规则。用户明确确认当前场景方案，可锁为 `scene_verified`；跨多个场景重复有效后再升级。

# 4. EDCM 导演认知覆盖矩阵

项目自定义工作名：`Epistemic Director Coverage Matrix`。

- **K0 明确已知**：用户明确确认、正式剧本、正式资产、canonical主档、一手证据。
- **K1 隐含已知**：从多次反馈和稳定选择中反推，但必须记录证据、置信度和边界。
- **K2 邻接未知**：用户未主动提出，但解释后可理解并能提升制作的专业知识；研究后先作为 candidate。
- **K3 unknown-unknown**：重复失败、旧技能解释不了、工具变化、技能冲突等暴露出的未知；先进入 Unknown Registry，不能直接变规则。

# 5. Final-Delta

当用户明确认为改后更好，至少回答：

1. 原方案真正的问题是什么？
2. 新方案改变了哪个因果、认知、表演、空间、声音或节奏变量？
3. 是否存在其他解释？
4. 如果把新技巧机械套到其他场景，会在哪里失败？
5. 它属于通用、项目、角色/场景还是一次性策略？
6. 需要什么真实生成或后续场景才能继续验证？

# 6. 写回事务

正式写回统一采用：

```text
FETCH current
→ EDIT
→ COMMIT serially
→ FETCH VERIFY
```

只有回读发现目标规则/条目且状态正确，才能对用户说“已录入 / 已登记 / 已修改”。

Memory、聊天摘要、临时文件和待合并草稿都不等于正式写回。

# 8. 角色自主生命连续性案例

当前代表性回归样本：菲奥奈在布道施粥广场原本就在带队巡查和维护秩序，高处异常只触发轻微职业警觉；队友拦下插队男子后，她回到职责协调。此案例用于验证“角色不是等镜头激活，而是镜头切到其原本正在继续的人生”。

# 9. 多轮修订收敛协议（Multi-Revision Consolidation Protocol）

当用户持续修改同一剧情段、镜头、提示词或 work item 时，不把每一轮都晋级为正式技能，也不能只看最终版本而丢失中间因果证据。

固定采用：

```text
Micro Capture
→ Constraint Ledger
→ Checkpoint
→ Trajectory Final-Delta
→ maturity / eval / regression
→ 正式写回
```

## 9.1 Revision Series

同一 work item 的连续修改形成 `R0 → R1 → R2 → R3 ...`。

每轮至少识别：

- `ADD`：新增要求；
- `MODIFY`：修改已有要求；
- `REVOKE`：明确取消已有要求；
- `EXPERIMENT`：试验性方案，未确认；
- `LOCK`：用户明确确认的当前有效决定。

中间 revision 是证据，不自动成为长期导演规则。

## 9.2 Constraint Ledger

当前有效状态遵循：

```text
Effective State
= Baseline
+ Accepted / Locked Deltas
- Explicitly Revoked Deltas
```

**省略不等于撤销。**

用户后续提示词没有重复写出之前已确认的要求时，不得自动视为取消。只有用户明确撤销，或新要求与旧要求存在不可兼容的明确冲突时，才允许标记 `REVOKE`；冲突不清时保留旧约束并提示风险。

每次新 revision 都应继承仍有效的剧情、角色、空间、资产、连续性与已接受导演约束。

## 9.3 Micro Capture

每次有实质修改时自动记录最小 Delta：

```yaml
revision_id:
parent_revision:
changed:
preserved:
revoked:
experimental:
user_reason:
observed_effect:
current_best:
```

Micro Capture 的目的只是保留因果轨迹，不要求每轮 GitHub commit，也不触发技能晋级。

## 9.4 自动 Checkpoint

出现任一条件时可自动形成轻量 Checkpoint：

- 连续约 3–5 次实质修改；
- 用户说“这个好多了 / 这样可以 / 这一版先用”等；
- work item 的关键约束已经稳定；
- 即将切换到下一镜、下一场或另一任务。

Checkpoint 保存：当前有效状态、accepted / locked constraints、revoked constraints、open experiments、current best、尚未解决的问题。

当前有效剧情/镜头生产状态按 `write_routes.yaml` 路由到连续性或对应 canonical；修订与学习证据进入反馈引擎。Checkpoint 不等于长期技能晋级。

## 9.5 语义自动收敛

当用户自然表达“好了，下一镜”“继续下面剧情”“换下一个场景”“这个问题解决了”“这一版就这样”，或语义上明显进入新的 work item 时，系统应在处理新 work item 前自动关闭上一 revision series，执行一次 Trajectory Final-Delta。无需用户额外下“总结/学习”命令。

如果只是暂时离开话题且是否结束不明确，不强行 final；保留可恢复 Checkpoint。

## 9.6 Trajectory Final-Delta

收敛时同时分析：

1. `Step Delta`：每一步改变了什么，哪些变化有效、无效或被撤回；
2. `Global Final-Delta`：R0 到当前最佳版本整体为什么更好；
3. 贡献归因：哪些变量真正解释改善，哪些只是同时变化；
4. 替代解释与反事实；
5. 适用范围与失败边界；
6. 是否形成可复用 candidate lesson；
7. 是否需要 targeted eval / regression。

不得把最终提示词整体机械复制成通用规则，应拆成可验证的最小知识单元。

# 10. 自动化权限与人工门

用户可专注于正常导演讨论，系统默认自动执行低风险学习管理：revision series 识别、Constraint Ledger、Micro Capture、Checkpoint、Final-Delta、学习证据写回、已明确确认的当前生产状态写回、`candidate` / 单场明确验证后的 `scene_verified` 记录、regression candidate，以及 FETCH → EDIT → COMMIT → FETCH VERIFY。

以下高影响操作不得因自动学习静默完成：

- `scene_verified → project_verified` 或更高成熟度晋级，若会显著扩大适用范围；
- 推翻核心剧情、世界观或角色身份；
- 改变 canonical 空间拓扑；
- 替换正式默认资产；
- 删除主档或大量内容；
- 新证据与稳定规则冲突且边界不清。

遇到这些情况，由系统主动提出最小必要人工确认，用户不需要日常主动管理学习系统。

# 11. 用户工作方式

用户正常流程应保持为：

```text
讨论
→ 修改
→ 看效果
→ 再修改
→ 确认或进入下一镜
```

其余 revision 管理、学习抽象、成熟度判断、回归与低风险 GitHub 写回由系统承担。用户不应被要求重复执行数据库式整理或手动触发 Final-Delta。
