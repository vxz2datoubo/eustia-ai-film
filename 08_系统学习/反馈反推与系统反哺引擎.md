# 反馈反推与系统反哺引擎

> 本文件负责把用户反馈与真实生成结果转成可验证的学习对象，并路由到唯一主文件。它不保存第二份规则副本。

# 1. 固定闭环

```text
先修当前结果
→ 比较修改前后
→ 判断真正解决了什么问题
→ 推测真实意图与价值排序
→ 区分临时要求和稳定规律
→ 做反事实与替代解释
→ 定义适用条件、边界、反例和失效条件
→ 标记成熟度
→ 写回唯一目标文件
→ 回读验证
→ 必要时增加回归案例
```

# 2. 学习成熟度

```text
candidate
→ scene_verified
→ project_verified
→ general_stable
```

旁路状态：

- `conflicted`：存在相反有效经验，按边界路由，不静默覆盖。
- `needs_revalidation`：模型、工具或版本变化使旧经验可能过期。
- `deprecated`：已被替代或证伪。

一次成功不能自动成为通用规则。用户明确确认当前场景方案，可锁为 `scene_verified`；跨多个场景重复有效后再升级。

# 4. EDCM 导演认知覆盖矩阵

项目自定义工作名：`Epistemic Director Coverage Matrix`。

- **K0 明确已知**：用户明确确认、正式剧本、正式资产、canonical主档、一手证据。
- **K1 隐含已知**：从多次反馈和稳定选择中反推，但必须记录证据、置信度和边界。
- **K2 邻接未知**：用户未主动提出，但解释后可理解并能提升制作的专业知识；研究后先作为 candidate。
- **K3 unknown-unknown**：重复失败、旧技能解释不了、工具变化、技能冲突等暴露出的未知；先进入 Unknown Registry，不能直接变规则。

# 5. Final-Delta

当用户明确认为改后更好，至少回答：

1. 原方案真正的问题是什么？
2. 新方案改变了哪个因果、认知、表演、空间、声音或节奏变量？
3. 是否存在其他解释？
4. 如果把新技巧机械套到其他场景，会在哪里失败？
5. 它属于通用、项目、角色/场景还是一次性策略？
6. 需要什么真实生成或后续场景才能继续验证？

# 6. 写回事务

正式写回统一采用：

```text
FETCH current
→ EDIT
→ COMMIT serially
→ FETCH VERIFY
```

只有回读发现目标规则/条目且状态正确，才能对用户说“已录入 / 已登记 / 已修改”。

Memory、聊天摘要、临时文件和待合并草稿都不等于正式写回。

# 8. 角色自主生命连续性案例

当前代表性回归样本：菲奥奈在布道施粥广场原本就在带队巡查和维护秩序，高处异常只触发轻微职业警觉；队友拦下插队男子后，她回到职责协调。此案例用于验证“角色不是等镜头激活，而是镜头切到其原本正在继续的人生”。

# 9. 任务问题归档闭环

任务发布者在发布前读取 `本地问题模式集合` 中与工具、格式和环境相关的 project_verified 条目，把对应 `task_release_check` 放进验收。执行者在任务结束时，对每个可复现的本地失败或修复记录条目，至少提供症状、根因（未知则标 candidate）、安全修复、实际验证和适用边界；由本引擎决定是否升级为通用规则或其他 canonical 的写回。
