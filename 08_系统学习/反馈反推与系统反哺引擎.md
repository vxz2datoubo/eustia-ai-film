# 反馈反推与系统反哺引擎

> 本文件负责把用户反馈与真实生成结果转成可验证的学习对象，并路由到唯一主文件。它不保存第二份规则副本。

# 1. 固定闭环

```text
先修当前结果
→ 比较修改前后
→ 判断真正解决了什么问题
→ 推测真实意图与价值排序
→ 区分临时要求和稳定规律
→ 做反事实与替代解释
→ 定义适用条件、边界、反例和失效条件
→ 标记成熟度
→ 写回唯一目标文件
→ 回读验证
→ 必要时增加回归案例
```

# 2. 学习成熟度

```text
candidate
→ scene_verified
→ project_verified
→ general_stable
```

旁路状态：

- `conflicted`：存在相反有效经验，按边界路由，不静默覆盖。
- `needs_revalidation`：模型、工具或版本变化使旧经验可能过期。
- `deprecated`：已被替代或证伪。

一次成功不能自动成为通用规则。用户明确确认当前场景方案，可锁为 `scene_verified`；跨多个场景重复有效后再升级。

# 4. EDCM 导演认知覆盖矩阵

项目自定义工作名：`Epistemic Director Coverage Matrix`。

- **K0 明确已知**：用户明确确认、正式剧本、正式资产、canonical主档、一手证据。
- **K1 隐含已知**：从多次反馈和稳定选择中反推，但必须记录证据、置信度和边界。
- **K2 邻接未知**：用户未主动提出，但解释后可理解并能提升制作的专业知识；研究后先作为 candidate。
- **K3 unknown-unknown**：重复失败、旧技能解释不了、工具变化、技能冲突等暴露出的未知；先进入 Unknown Registry，不能直接变规则。

# 5. Final-Delta

当用户明确认为改后更好，至少回答：

1. 原方案真正的问题是什么？
2. 新方案改变了哪个因果、认知、表演、空间、声音或节奏变量？
3. 是否存在其他解释？
4. 如果把新技巧机械套到其他场景，会在哪里失败？
5. 它属于通用、项目、角色/场景还是一次性策略？
6. 需要什么真实生成或后续场景才能继续验证？

# 6. 写回事务

正式写回统一采用：

```text
FETCH current
→ EDIT
→ COMMIT serially
→ FETCH VERIFY
```

只有回读发现目标规则/条目且状态正确，才能对用户说“已录入 / 已登记 / 已修改”。

Memory、聊天摘要、临时文件和待合并草稿都不等于正式写回。

# 8. 角色自主生命连续性案例

当前代表性回归样本：菲奥奈在布道施粥广场原本就在带队巡查和维护秩序，高处异常只触发轻微职业警觉；队友拦下插队男子后，她回到职责协调。此案例用于验证“角色不是等镜头激活，而是镜头切到其原本正在继续的人生”。

# 9. 多轮修订收敛协议（Multi-Revision Consolidation Protocol）

当用户持续修改同一剧情段、镜头、提示词或 work item 时，不把每一轮都晋级为正式技能，也不能只看最终版本而丢失中间因果证据。

固定采用：

```text
Micro Capture
→ Constraint Ledger
→ Checkpoint
→ Trajectory Final-Delta
→ maturity / eval / regression
→ 正式写回
```

## 9.1 Revision Series

同一 work item 的连续修改形成 `R0 → R1 → R2 → R3 ...`。

每轮至少识别：

- `ADD`：新增要求；
- `MODIFY`：修改已有要求；
- `REVOKE`：明确取消已有要求；
- `EXPERIMENT`：试验性方案，未确认；
- `LOCK`：用户明确确认的当前有效决定。

中间 revision 是证据，不自动成为长期导演规则。

## 9.2 Constraint Ledger

当前有效状态遵循：

```text
Effective State
= Baseline
+ Accepted / Locked Deltas
- Explicitly Revoked Deltas
```

**省略不等于撤销。**

用户后续提示词没有重复写出之前已确认的要求时，不得自动视为取消。只有用户明确撤销，或新要求与旧要求存在不可兼容的明确冲突时，才允许标记 `REVOKE`；冲突不清时保留旧约束并提示风险。

每次新 revision 都应继承仍有效的剧情、角色、空间、资产、连续性与已接受导演约束。

## 9.3 Micro Capture

每次有实质修改时自动记录最小 Delta：

```yaml
revision_id:
parent_revision:
changed:
preserved:
revoked:
experimental:
user_reason:
observed_effect:
current_best:
```

Micro Capture 的目的只是保留因果轨迹，不要求每轮 GitHub commit，也不触发技能晋级。

## 9.4 自动 Checkpoint

出现任一条件时可自动形成轻量 Checkpoint：

- 连续约 3–5 次实质修改；
- 用户说“这个好多了 / 这样可以 / 这一版先用”等；
- work item 的关键约束已经稳定；
- 即将切换到下一镜、下一场或另一任务。

Checkpoint 保存：当前有效状态、accepted / locked constraints、revoked constraints、open experiments、current best、尚未解决的问题。

当前有效剧情/镜头生产状态按 `write_routes.yaml` 路由到连续性或对应 canonical；修订与学习证据进入反馈引擎。Checkpoint 不等于长期技能晋级。

## 9.5 语义自动收敛

当用户自然表达“好了，下一镜”“继续下面剧情”“换下一个场景”“这个问题解决了”“这一版就这样”，或语义上明显进入新的 work item 时，系统应在处理新 work item 前自动关闭上一 revision series，执行一次 Trajectory Final-Delta。无需用户额外下“总结/学习”命令。

如果只是暂时离开话题且是否结束不明确，不强行 final；保留可恢复 Checkpoint。

## 9.6 Trajectory Final-Delta

收敛时同时分析：

1. `Step Delta`：每一步改变了什么，哪些变化有效、无效或被撤回；
2. `Global Final-Delta`：R0 到当前最佳版本整体为什么更好；
3. 贡献归因：哪些变量真正解释改善，哪些只是同时变化；
4. 替代解释与反事实；
5. 适用范围与失败边界；
6. 是否形成可复用 candidate lesson；
7. 是否需要 targeted eval / regression。

不得把最终提示词整体机械复制成通用规则，应拆成可验证的最小知识单元。

# 10. 自动化权限与人工门

用户可专注于正常导演讨论，系统默认自动执行低风险学习管理：revision series 识别、Constraint Ledger、Micro Capture、Checkpoint、Final-Delta、学习证据写回、已明确确认的当前生产状态写回、`candidate` / 单场明确验证后的 `scene_verified` 记录、regression candidate，以及 FETCH → EDIT → COMMIT → FETCH VERIFY。

以下高影响操作不得因自动学习静默完成：

- `scene_verified → project_verified` 或更高成熟度晋级，若会显著扩大适用范围；
- 推翻核心剧情、世界观或角色身份；
- 改变 canonical 空间拓扑；
- 替换正式默认资产；
- 删除主档或大量内容；
- 新证据与稳定规则冲突且边界不清。

遇到这些情况，由系统主动提出最小必要人工确认，用户不需要日常主动管理学习系统。

# 11. 用户工作方式

用户正常流程应保持为：

```text
讨论
→ 修改
→ 看效果
→ 再修改
→ 确认或进入下一镜
```

其余 revision 管理、学习抽象、成熟度判断、回归与低风险 GitHub 写回由系统承担。用户不应被要求重复执行数据库式整理或手动触发 Final-Delta。

# 12. 屏幕证据化提示词编译｜SCREEN-EVIDENCE-001

状态：`candidate`

## 12.1 本次反馈来源

用户指出：AI电影执行稿中的“凯姆已经在数层高的民房外墙上快速攀爬”过于概念化。对视频模型而言，“数层高”“很高”“快速”等词把关键画面留给模型自行解释；更有效的写法应直接描述屏幕上实际可见的楼层锚点、地面高差、人物相对位置、动作接触点与运动方向，同时避免为了消除歧义继续无限增加约束。

本轮属于导演执行稿的表达层修正，不改变剧情、空间拓扑或人物目标。

## 12.2 观察到的问题

```yaml
feedback_id: SCREEN-EVIDENCE-001
work_item_id: KAIM-HIGH-SEARCH-30S
observed_problem:
  - 概念总结词承担了关键空间和动作信息
  - 模型需要自行把“数层高/很高/很快”翻译成具体画面
  - 抽象词与大量禁止项叠加后可能提高解释自由度而非降低歧义
real_goal:
  - 让AI直接接收到接近最终屏幕画面的可执行轮廓
  - 保留足够模型自主性，不把提示词写成逐像素或逐秒控制表
value_priority:
  - 可观察性
  - 低歧义
  - 最小充分
  - 真实物理关系
  - 模型自主节奏
maturity: candidate
```

## 12.3 外部证据与可信度边界

### T1 / 官方模型资料

1. 字节跳动 Seed 官方 Seedance 页面明确强调原生多镜头叙事、复杂自然语言指令、多主体互动、多重动作组合与运镜控制；Seedance 2.0 官方页面进一步强调多模态音视频联合生成、物理规律还原以及对表演、光影、运镜的导演级操控。
2. Runway 官方 Gen-4 / Gen-4.5 Prompting Guide 明确建议使用直接、简单、易理解的提示，避免用抽象概念代替具体物理动作；对于图生视频，输入图已承担主体、构图、颜色、光线与风格等视觉信息，文本应主要补充动作、摄影机与时间推进；同时官方提醒过度复杂、逐秒塞入过多变化会提高失败风险。

证据边界：Runway 是跨模型工程证据，不能冒充 Seedance 2.5 官方规范；字节官方当前公开页面支持 Seedance 系列的多镜头、动作、运镜、物理与多模态能力，但本次“屏幕证据化写法”是否在 Seedance 2.5 上显著优于概念写法，仍需本项目真实生成 A/B 验证。因此本条保持 `candidate`，不得因理论一致就晋级为 `scene_verified`。

## 12.4 第一性原理

AI视频执行稿的关键任务不是向人类解释“作者想表达什么”，而是向生成模型提供足以构成画面和运动的可观察条件。

```text
抽象导演意图
→ 判断哪些信息必须在屏幕上被看见
→ 为这些信息寻找最少量的视觉/动作证据
→ 编译成当前画面 + 空间关系 + 动作因果 + 环境反应 + 最终状态
→ 把非关键细节留给模型自主完成
```

因此：

> 少写“结论”，多写让模型能够生成该结论的屏幕证据；但屏幕证据也必须遵守最小充分原则，不因追求具体而滑向过度约束。

## 12.5 默认编译结构

影视剧情型 Seedance 执行稿遇到高度、尺度、速度、危险、距离、空间关系或复杂动作时，优先检查以下五类信息：

1. **当前可见画面轮廓**：镜头此刻能看见谁、什么结构、什么前中后景。
2. **空间与尺度证据**：楼层、窗、地面、人群、道路、屋檐等相对锚点，让高度与距离从画面关系中成立。
3. **物理动作链**：手抓哪里、脚踩哪里、身体怎样转移重心、下一步去哪里；只保留关键接触点，不写无意义微动作清单。
4. **环境反应**：窗扇震动、灰尘、衣料、物件、旁人反应等能证明动作真实发生的反馈；无叙事价值时不强行添加。
5. **最终状态**：本镜结束时人物、摄影机、目标与空间关系停在哪里，为下一镜提供稳定接口。

推荐编译顺序：

```text
VISIBLE FRAME
→ RELATIVE SPATIAL EVIDENCE
→ PHYSICAL ACTION CHAIN
→ ENVIRONMENT RESPONSE（按需）
→ FINAL STATE
```

## 12.6 抽象词转屏幕证据映射

抽象词可以保留为导演意图或辅助风格，但不能单独承担关键可执行信息。

| 抽象概念 | 优先转译的屏幕证据 |
|---|---|
| 很高 / 数层高 | 已越过的楼层锚点、下方街面、人群尺度、窗与屋檐相对位置、俯视落差 |
| 很快 | 连续动作接触点、短停留、惯性、环境响应、前后位置变化 |
| 轻盈 | 少量有效借力、短接触、重心连续、无多余停顿，而非写“像轻功” |
| 危险 | 可见落差、窄支撑面、接触失败后果、障碍或逼近关系 |
| 压迫 | 占幅、遮挡、距离缩短、负空间减少、静止权，而非只写“压迫感” |
| 混乱 | 多个互不完全同步的局部行为、人流阻塞、视线竞争、声音层，而非所有人一起乱跑 |
| 专业 / 熟练 | 动作选择正确、预判、少量调整、连续执行，而非“动作非常专业” |

## 12.7 模态职责分流

### 文生视频 T2V

文字需要承担较多的初始画面建立职责，因此应给出必要的主体、场景结构、相对位置、动作和摄影机轮廓。

### 图生视频 / 多模态 I2V

参考图已经明确的主体外观、构图、光线、材质与静态空间不应在文本里高密度重复。文本优先补充：

- 当前图中无法表达的动作顺序；
- 接触与重心；
- 摄影机运动；
- 环境动态反馈；
- 关键空间关系变化；
- 声音与时间推进；
- 最终状态。

如果参考图没有可靠表达关键高度、方向、遮挡或接触关系，则仍需补充最小必要视觉锚点。

## 12.8 Prompt Constraint Budget｜约束预算

屏幕证据化不等于把每个像素都写出来。

默认只保留三类信息：

1. **剧情必须成立**：不写会改变事件因果、揭示或人物行为。
2. **模型容易误解**：高度、方向、施力者、接触点、多人绑定等。
3. **下一镜必须继承**：人物位置、道具归属、摄影机方向、最终状态。

可以交给模型自主发挥：

- 不影响剧情的群众小动作；
- 非关键微材质变化；
- 不改变空间和身份的自然呼吸、衣摆、风、尘等次级运动；
- Seedance 能自然完成且无历史失败证据的镜头时长分配。

若提示词为了“更准确”持续增加同义形容词、重复否定、逐秒动作和静态画面复述，应触发 `prompt_constraint_budget` 扫描并主动删减。

## 12.9 与现有技能联动

- 与 `时间码按需控制` 联动：屏幕证据描述事件顺序，不等于强制逐秒时间码。
- 与 `空间拓扑先行` 联动：具体化空间前必须先服从 canonical 地图；具体写错比抽象写法危害更大。
- 与 `CALC / CLCS` 联动：不仅写“角色在巡查”，还应给出可见的既有活动证据。
- 与 `叙事并行化` 联动：画面证据和 VO / 声音可同时承担不同信息，不让解释冻结画面。
- 与 `主导变化律` 联动：具体画面仍围绕一个主要变化，不因为证据化而引入多个竞争事件。
- 与 `模型自主权合同` 联动：关键证据 LOCKED / GUIDED，非关键细节 FREE。
- 与 `局部失败定位` 联动：高度失败补高度证据，动作漂浮补接触与重心，空间漂移补地图/几何，不用整段继续加词。

## 12.10 反例与失效边界

以下情况不能机械套用“越具体越好”：

- 参考图已经精确锁定静态画面时，重复描述大量现有像素可能挤压动作信息预算。
- 需要模型自然发挥表演细节时，过度指定每个手指、每一步和每次眨眼会使运动僵硬或互相冲突。
- 纯情绪或风格意图仍可使用少量抽象词，但关键剧情动作和空间关系必须另有可观察证据。
- 严格顶视、几何测绘、产品结构、文字 Logo 等高精度任务，本来就需要更多显式锁定，不能用“少约束”作为借口降低几何合同。
- 不同模型版本的提示词敏感度可能变化；Seedance 2.5 版本变化或实测反例出现时转入 `needs_revalidation`。

## 12.11 Targeted Eval

当前回归候选：`REG-SCREEN-EVIDENCE-001`。

后续在凯姆攀爬段或其他至少一个不同场景进行 A/B：

```text
A：概念概括为主
B：最小充分屏幕证据化
```

比较至少：

- 指令遵循；
- 高度/尺度可读性；
- 身体接触与物理合理性；
- 动作连续性；
- 镜头空间稳定；
- 是否出现多余模型脑补；
- 提示词复杂度；
- 是否因约束增加导致运动僵硬。

只有真实结果证明 B 在目标维度更优且未显著伤害其他维度，才可从 `candidate` 晋级 `scene_verified`；跨多个不同场景重复成立后再考虑 `project_verified`。

# 13. 正向动作规格与否定约束预算｜POSITIVE-SPEC-001

通用规则状态：`candidate`

场景失败观察：`scene_verified observation / E4`

## 13.1 真实生成反馈

当前 work item：`KAIM-HIGH-SEARCH-30S`。

上一版 Seedance 2.5 执行稿包含：

- “没有炫耀感”；
- “不飞跃”；
- “不悬空”；
- “不做超级英雄式动作”；
- “摄影机不围绕人物炫技”。

用户真实生成结果：凯姆没有形成预期的外立面轻功 / 跑酷式连续上行，而是出现“爬楼梯”式替代行为。该结果在字面上满足“不飞跃、不悬空”，却违背“沿建筑外墙借支点轻盈快速向上”的真实导演意图。

因此本次要区分：

1. **观测事实**：该提示组合在该场景产生了错误替代路线。已由用户真实生成确认，E4。
2. **因果解释**：强绝对否定压缩了模型可选择的动作集合，模型转而找到更容易满足字面约束的低风险动作。高置信推断，但尚未做控制变量 A/B。
3. **可迁移规则**：正向动作规格 + 少量局部硬约束通常比大量全局绝对否定更适合作为影视动作控制。当前为 candidate，等待跨场景验证。

## 13.2 与上一条 SCREEN-EVIDENCE-001 的关系

`SCREEN-EVIDENCE-001` 解决“你到底想让屏幕出现什么”。

`POSITIVE-SPEC-001` 解决“如何把这些屏幕证据告诉模型，而不因排除错误把正确动作也一起砍掉”。

组合编译链：

```text
导演意图
→ SCREEN EVIDENCE：画面上必须看见什么
→ POSITIVE TARGET：正确动作实际怎样发生
→ MOTION ENVELOPE：允许模型在哪些范围内自然发挥
→ HARD INVARIANTS：极少数绝不能破坏的剧情/身份/拓扑事实
→ LOCAL EXCLUSION（必要时）：只排除一个明确且严重的错误模式
→ FINAL STATE
```

## 13.3 第一性原理：定义正确解，而不是枚举错误解

对生成模型而言，导演最需要定义的是**目标轨迹**而不是“所有不允许发生的轨迹”。

错误控制方式：

```text
希望动作A
- 不要错误B
- 不要错误C
- 不要错误D
- 不要错误E
```

当 B/C/D/E 的作用域过大，可能连 A 中必需的局部动作成分也一起排除。凯姆跑酷攀墙就是典型：正常上行需要在相邻支点之间短暂离墙、腾跃和重新接触；“不飞跃、不悬空”把这些正常中间态也做成了禁区。

推荐控制方式：

```text
正向描述动作A的可见步骤
+ 给出A成立所需的物理支点、重心、跃距/离墙时间等运动边界
+ 只锁真正不可破坏的不变量
```

## 13.4 Positive Action Envelope｜正向动作包络

不把动作锁成一条逐帧脚本，而是给出“允许的正确动作空间”。

凯姆外墙上行可表达为：

- 路线始终沿建筑外立面向上；
- 手、脚不断利用突出石块、横梁、窗框、窗台、屋檐等真实支点；
- 相邻支点之间允许短距离离墙腾跃；
- 离墙后迅速抓住或踩住下一处支点；
- 每次发力都让身体重心继续向上；
- 接触短、停顿少、路线连续；
- 摄影机沿他的上行路径抬升和轻微修正，同时保持人物与下一处支点可读。

这套写法允许“轻盈”所必需的小幅腾跃与短暂悬空，又用支点、落点和重心保持真实物理，不需要写“绝不悬空”。

## 13.5 Hard / Soft / Free 三层约束

### HARD｜真正硬不变量

只给会改变成片事实的内容：

- 角色身份；
- canonical 空间拓扑；
- 关键道具归属；
- 必须保护的揭示预算；
- 动作因果中施力者 / 被作用者；
- 最终状态接口；
- 特殊几何镜头必须锁定的摄影机自由度。

优先用正向状态表达；实在无法正向表达时才保留局部排除。

### SOFT / GUIDED｜风格与动作边界

例如：

- 跑酷式上行；
- 腾跃只发生在相邻支点之间；
- 离墙阶段短；
- 动作紧凑但有真实惯性；
- 摄影机跟随路线而不是自行成为表演主体。

这类不使用“100%绝不”的语言。

### FREE｜模型可自由补全

- 非关键手脚微调；
- 呼吸；
- 衣摆与尘土；
- 无关群众微动作；
- Seedance 已表现稳定的自然镜头时长分配。

## 13.6 否定约束的四类处理

### A. 可正向重写的否定

默认删除否定，改写目标画面。

| 原否定 | 推荐正向规格 |
|---|---|
| 不飞跃 | 在相邻建筑支点之间做短距离腾跃并立即接住下一支点 |
| 不悬空 | 每次离墙阶段都短促并指向下一处可见抓点或落点 |
| 不做超级英雄动作 | 所有上升动力来自可见石沿、横梁、窗框、屋檐等建筑支点，跃距保持在相邻支点范围 |
| 摄影机不围绕人物炫技 | 摄影机沿人物上行路径抬升与轻微横向修正，始终让人物和下一支点同时可读 |
| 不要所有人乱跑 | 群众各自沿排队、取粥、搬运和通行的小目标活动，局部节奏不同 |
| 不出现天空 | 上方画面由相邻高墙、屋檐、岩壁或建筑结构填满，构图保持封闭 |

### B. 平台专用 negative-prompt 通道

如果模型有官方独立 negative prompt 字段，必须按该平台官方语义使用。专用负向通道不能和主提示里的自然语言“不 / 不要 / 绝不”视为同一机制。

### C. 关键硬排除

当错误会直接破坏剧情、身份、拓扑或悬念，并且正向规格仍不足以保护时，可以保留少量局部排除。例如“这一镜目标男孩保持在镜外，翅膀揭示留给后续场次”优于连续罗列多个“不要展示男孩 / 不要展示翅膀 / 不要发现目标”。

### D. 质量词式负面清单

“非CG、非游戏、非插画、不要塑料、不要低清、不要HDR……”若每镜重复，会形成提示预算污染。已有稳定视觉资产 / 风格母版时，应由正向风格规格和参考资产承担主要职责；只有真实历史失败反复出现的高风险项才保留。

## 13.7 为什么会出现“爬楼梯”｜可行解空间与替代行为

这是项目推断，不冒充 Seedance 内部算法说明。

可以把模型候选动作想象成一组轨迹：

```text
外墙连续借力
短跃到窗台
抓横梁上提
沿屋檐翻越
爬梯
走室内楼梯
其他模型自发路线
```

如果主提示同时施加：

```text
不飞跃
不悬空
不超级英雄
```

那么本来正确的跑酷轨迹中许多必要中间态都会与否定语义发生冲突。模型仍要完成“向上”，就更容易转向“手脚持续接触稳定结构”的替代路线，例如楼梯。

这与 Google DeepMind 所讨论的 `specification gaming` 有结构类比：系统满足字面 specification，却没有实现设计者真正想要的结果。但这里不声称 Seedance 在进行 RL reward hacking，只借用“字面合规 ≠ 意图合规”的规格设计视角。

## 13.8 外部研究交叉验证

### Runway 官方｜强支持

Gen-4 Video 官方提示指南明确推荐 positive phrasing，并指出 negative prompting 可能产生不可预测或相反结果；同时要求把概念意图转成明确物理动作。这与本次 E4 失败高度一致，但属于跨模型证据。

### Google Veo 官方｜强支持但机制不同

Veo 有专用 negative prompt 工具，但官方仍明确不推荐用“no / don't”式指令语言；应描述要排除的元素。说明“自然语言否定句”和“专门负向控制机制”应分开看。

### ByteDance Seedance 官方｜部分直接支持

Seedance 官方资料确认模型能理解复杂动作、多主体互动、运镜与多模态分镜，并强调运动稳定和物理还原；公开示例以正向动作描述为主。但本次检索没有取得 Seedance 2.5 对否定作用域或专用 negative prompt 的公开精确定义，因此不能声称“字节官方规定禁止否定词”。

### NegVQA / NEGATE｜理论支持

ACL 2025 NegVQA 显示多类 VLM 对 negation 的理解显著弱于原问题；2026 T2V 预印本 NEGATE 将 linguistic negation 作为需要专门结构化 guidance 处理的问题。它们支持“否定不是天然稳定语义算子”，但不能直接证明 Seedance 2.5 的具体内部机制。

## 13.9 与现有项目技能联动

- `SCREEN-EVIDENCE-001`：先确定正确画面，再正向描述；二者是上下游关系。
- `Prompt Constraint Budget`：否定句和禁止项也占控制预算；默认先删重复、全局、绝对的负约束。
- `模型自主权合同`：HARD 只锁真正不变量；动作风格多数为 GUIDED，不要误锁成 HARD。
- `空间拓扑先行`：用真实建筑支点定义动作包络，避免模型用楼梯等替代空间偷换路线。
- `白模 / 动作参考`：复杂跑酷若文字仍不稳定，用动作视频或白模提供正向轨迹，比继续增加否定词更可靠。
- `局部失败定位`：出现“爬楼梯”时优先检查负约束是否压缩了正确动作空间，而不是继续加“不要爬楼梯”。
- `时间码按需`：正向动作顺序不等于逐秒控制；仍让 Seedance 自主分配镜头时长。
- `CALC / CLCS`：人物行为应正向体现他正在做什么，不用“不是站着等剧情”作为最终模型执行语言。

## 13.10 失效边界

本规则不能被机械简化成“永远不能写否定词”。

以下情况仍可能需要排除控制：

- 明确的剧情 reveal 保护；
- 角色身份错位；
- canonical 空间拓扑被模型反复改错；
- Logo / 文字 / 产品结构等严格交付；
- 平台有独立、官方支持的 negative-prompt 通道；
- 某个失败模式已被多次真实验证，且正向规格无法单独消除。

即便保留，也应遵守：**局部、对象明确、作用域明确、数量最少、不得误杀正确动作所需中间态。**

# 14. 单镜头可观察域与跨镜头信息隔离｜SHOT-SCOPE-001

通用规则状态：`candidate`

场景失败观察：`scene_verified observation / E4`

## 14.1 真实生成反馈

当前 work item：`KAIM-HIGH-SEARCH-30S`。

真实 Seedance 2.5 输出与用户逐镜核对暴露出一组互相关联的问题：

- 农妇仍处于“摄影机在窗外看向农妇”的反应镜头时，执行稿已经写入下一主观镜头才应出现的下方街道、人群、广场、钟楼与猎羽信息；
- 爱丽丝只承担 VO，却在生成结果中被实体化进广场人群；
- 农妇的观察镜头与随后主观镜头没有清楚分域，导致视点高度、画面内容和空间揭示混乱；
- 全局剧情因果对人类导演是正确的，但把它直接倾倒进逐镜执行稿后，模型可能把“全局知道”误当成“当前画面应出现”。

用户明确提出：每个镜头的最终 AI 视频描述必须只写当前摄影机实际能看见 / 能听见的内容；知道但当前镜头看不到的剧情事实、角色、空间和下一镜揭示内容留在内部规划层。

## 14.2 第一性原理：Global Story State ≠ Shot Observable State

AI 电影系统可以拥有完整世界状态、剧情因果和下一镜计划，但视频渲染模型接收的是一个具体 shot 的生成条件。

因此必须区分：

```text
GLOBAL STORY STATE
= 全局剧情、角色、空间、因果、后续揭示、镜头组目的

SHOT OBSERVABLE STATE
= 当前camera state下真正可见 / 可听 / 将在本shot内实际被揭示的内容
```

最终执行稿不能把前者原样复制成后者。

## 14.3 Shot-local Prompt Compiler

复杂剧情先在内部完成全局导演规划，再逐 shot 编译：

```text
GLOBAL PLAN（internal only）
→ SHOT BOUNDARY
→ CAMERA STATE
→ VISIBLE SET
→ AUDIBLE SET
→ ON-SCREEN ACTION / CHANGE
→ IN-SHOT CAMERA REVEAL（按需）
→ EXIT STATE
→ NEXT-SHOT CONTRACT
```

给视频模型的当前 shot 文本主要来自 `CAMERA STATE + VISIBLE SET + AUDIBLE SET + ACTION/CHANGE + IN-SHOT REVEAL + EXIT STATE`。

`GLOBAL PLAN`、未来 reveal 和镜头外知识继续留在内部，不因导演知道它们就自动进入当前画面描述。

## 14.4 Visible Set｜当前可见集合

当前 shot 允许描述：

- 当前摄影机位置、朝向、景别与必要运动；
- 真实出现在画幅内的前景、中景、后景；
- 当前时刻能看到的角色、道具、建筑与环境；
- 当前 shot 内角色从左 / 右 / 前 / 后入画、出画或改变位置；
- 当前 shot 内真正发生的动作、接触、环境反应和可见结果。

前景 / 中景 / 后景不是“世界里存在什么”的清单，而是**当前 camera state 实际能看到什么**的分层。

若一个元素在当前构图中不可见，也不会在本 shot 的摄影机运动中被 reveal，它不能作为当前画面的前景 / 中景 / 后景写进生成执行稿。

## 14.5 Camera Reveal｜同一镜头内可见域可以随摄影机变化

SHOT-SCOPE 不等于“一个 shot 只能描述第一帧”。

若摄影机在同一连续镜头内真实改变视野，可以按时间因果描述可见域扩张：

```text
开始：摄影机在窗外看农妇，画面只有农妇、窗框、打开的窗扇和局部外墙。
→ 农妇向外、向下看。
→ 如果保持同镜并由摄影机随后绕到她的视线方向，写“摄影机移到她肩后 / 转向她的视线方向，随后揭示下方街道与广场”。
```

只有在摄影机实际完成 reveal 之后，新的区域和实体才进入当前 shot 的 visible set。

若通过剪辑切到另一个视点，则新内容属于下一 shot。

## 14.6 Audible Set｜镜外可听信息与视觉实体分离

当前镜头可以包含看不见但能听见的内容：

- VO / 画外音；
- 镜外对白；
- 远处钟声；
- 街市声；
- 镜外脚步、碰撞或环境声。

这些内容进入 `AUDIBLE SET`，不能因为文本里出现了角色名字就自动进入 `VISIBLE SET`。

特别是 VO：

```text
爱丽丝 VO = 声音通道的说话者
≠ 当前 shot 的可见角色
```

当人物只承担 VO 时，最终提示词应把其名字与台词绑定到声音职责，而不是在当前场景人物清单中重复出现。

## 14.7 Reaction Shot → POV / Reveal 的编译方式

以当前农妇镜头为代表：

### Shot A｜农妇反应镜头

当前 camera state：摄影机在建筑外侧，朝窗口和农妇。

合法 visible set：

- 二层窗口；
- 窗框；
- 已打开的木质窗扇；

这样“她在看什么”由 Shot B 负责揭示，不在 Shot A 抢跑。

## 14.8 与白模 / 因果连续分镜的联动

信息密度驱动的白模连续分镜也必须服从 shot scope。

- 白模图表达的是某一 shot / action-state 真正可见的几何、站位、接触和摄影机关系；
- 同一 shot 内的高密度动作可用 2–4 张连续白模表达状态变化；
- 下一 shot 才出现的实体和空间不提前塞入上一 shot 白模；
- 白模负责当前 shot 的 pose / layout / camera geometry，文字负责当前 shot 的 motion / temporal progression / causal change；
- 全局故事和未来信息继续由内部 plan / continuity / next-shot contract 保存。

这与 2026 `DrawVideo` 的 storyboard + appearance + motion 分工方向相邻，但当前项目只把它作为候选工程启发，需 Seedance 2.5 实测验证。

## 14.9 与现有技能联动

- `SCREEN-EVIDENCE-001`：屏幕证据先增加一个合法性检查，只有**当前 shot 合法可见**的证据才能进入当前执行稿；如果关键证据不在当前可见域，要么换镜头，要么放到下一 shot reveal。
- `EVENT-SEQUENCE-EXPLICIT-001`：先后关系不仅存在于动作内部，也存在于 shot boundary；“先看角色反应，再切 POV 揭示目标”属于跨 shot 因果顺序。
- `观众认知时差 / 延迟揭示`：未来目标不能因为内部已知而提前写入当前 visible set。
- `声音可观察化 / 声画分工`：VO、镜外声和可见实体分别进入 audible / visible 作用域，降低声音人物被错误实体化。
- `参考职责图`：白模、关键帧、场景图只负责它们对应 shot 的合法内容，不把参考图中的无关人物或后续场景自动扩散到其他镜头。
- `模型自主权合同`：shot boundary、camera state、关键 visible entities 与 reveal 时点可按风险设为 LOCKED / GUIDED；非关键环境微动作保持 FREE。
- `Prompt Constraint Budget`：隔离镜头外信息本身就是删减无效 token，不需要再用大量“不要出现某某”补救。
- `局部失败定位`：若出现错误角色、提前出现背景或 POV 错位，先扫描 cross-shot leakage，而不是继续在当前镜头增加更多全局说明。

## 14.10 边界与例外

本规则不能机械简化成“当前 prompt 只能写当前这一帧”。

允许：

- 同一连续 shot 内由摄影机运动真实 reveal 的新区域和主体，按先后顺序写入；
- 反射、玻璃、镜子、开口等只要实际出现在画面中，就属于 visible set；
- 镜外但当前可听见的声音进入 audible set；
- T2V 没有参考图时，为建立当前 shot 所需的可见环境可以写得更完整；
- 多镜头生成需要共用的身份、风格、canonical 拓扑等不变量可以在内部 / 顶层合同维护，但不把每个后续镜头的剧情实体复制进所有 shot。

不允许：

- 因为导演知道目标在画外，就在当前反应镜头的背景描述里提前加入目标；
- 把下一 shot 的建立镜头信息写成当前 shot 的前景 / 中景 / 后景；
- 把 VO 说话者默认生成成当前可见角色；
- 用“整体叙事总结”替代逐 shot 可观察描述。
