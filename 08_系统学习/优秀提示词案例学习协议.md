# 优秀提示词案例学习协议｜Golden Prompt Case Learning Protocol（GPCL）

> 本文件是 `08_系统学习/反馈反推与系统反哺引擎.md` 的专项摄取协议，只负责“用户明确判定为优秀提示词/优秀案例”时如何学习与登记，不建立第二套通用导演规则。抽取出的技能仍按 `10_运行时/write_routes.yaml` 写入唯一领域 canonical；成熟度仍服从 `10_运行时/maturity_model.yaml`。

# 1. 用户侧只有两个动作

当用户明确把一个提示词判定为“优秀提示词 / 优秀案例 / 以后作为参考案例 / 录入优秀案例”时，系统自动完成且只向用户呈现两个结果：

```text
STEP 1  LEARN
从优秀案例中学习系统可复用知识

STEP 2  REGISTER
把案例原文与证据直接登记进 Golden Prompt Case 库
```

用户不需要额外执行“总结、抽技能、建回归、写数据库、打标签、同步 GitHub”等动作。

## 1.1 强触发

以下语义属于 Golden Prompt Case 强触发：

- “这是优秀提示词”
- “这个提示词作为优秀案例”
- “把这个录入优秀案例”
- “以后参考这一版提示词”
- “这一版是我认可的优秀范例”

只要语义明确，不要求固定口令。

## 1.2 弱反馈不自动等同 Golden Case

“这样可以 / 这版先用 / 好多了 / 继续下一镜”等仍按 revision checkpoint / scene feedback 处理；除非用户明确表达“优秀案例 / 以后作为参考范例”等长期参考意图，否则不把整段提示词自动晋升成 Golden Case。

原因：`好用一次`、`当前可用`、`值得长期作为范例` 是三个不同判断，不能静默混为一谈。

# 2. 两类记忆必须分离

优秀提示词系统采用双记忆结构：

```text
EPISODIC CASE MEMORY
= 具体案例、原提示词、上下文、模型、资产、结果、用户评价

SEMANTIC SKILL MEMORY
= 从一个或多个案例中抽出的可迁移规则、边界、失败条件与调用条件
```

对应项目职责：

- Case Memory → `11_验收/golden_prompt_cases.yaml`
- Skill Memory → 按 `write_routes.yaml` 写入 AI电影系统、声音系统、SUNO词库、角色库、场景库等唯一 canonical
- 学习轨迹 / 因果分析 → 反馈反推与系统反哺引擎或其专项学习记录
- 专项外部证据 → `09_资料证据/优秀提示词案例学习证据索引.md`
- 协议回归 → `11_验收/golden_prompt_regression_cases.yaml`

**禁止把整条优秀提示词机械复制进“通用技能规则”。**

# 3. 用户四层认知映射 → EDCM

用户要求覆盖“我知道我说了 + 我知道但没说 + 我不知道但我看得懂 + 我不知道且我看不懂”。本协议直接复用项目现有 EDCM，不再另造重复体系。

| 用户认知层 | EDCM | 本协议处理 |
|---|---|---|
| 我知道，我也说了 | K0 明确已知 | 原提示词、用户明确评价、明确目标、明确约束、明确模型/资产等原样保存 |
| 我知道，但我没说全 | K1 隐含已知 | 从多轮 revision、稳定选择、删改与偏好反推隐藏目标；必须给证据、置信度与边界 |
| 我原来不知道，但解释后我看得懂 | K2 邻接未知 | 主动映射专业术语、导演/提示工程/评估/认知/软件工程等邻接知识；研究后先 candidate |
| 我原来不知道，而且当前也难以理解/验证 | K3 unknown-unknown | 不强行编成规则；登记 UNKNOWN / research question / experiment，等待外部证据或真实生成暴露 |

K0/K1/K2/K3 不是知识等级高低，而是当前证据与认知覆盖状态。

# 4. STEP 1｜LEARN：从优秀案例学习

每个强触发案例自动执行以下内部流程。

## 4.1 Source Lock｜先锁住原案例

在任何总结、改写、压缩前，先冻结：

- `source_prompt_verbatim`
- 用户原始评价
- 当前 work item / scene / shot
- 模型与版本（能确认时）
- T2V / I2V / multimodal / edit 等生成模式
- 参考图、资产、白模、首尾帧等依赖（能确认时）
- 生成参数（能确认时）
- 用户是在评价“提示词文本”，还是“真实生成结果”，还是两者

不得用系统改写版覆盖用户原文。

## 4.2 Verdict Scope｜先判断“优秀”到底指什么

至少区分：

- `prompt_approved`：用户认为提示词本身优秀；
- `output_verified`：用户看过真实生成结果并认为优秀；
- `comparative_win`：相对上一版 / baseline 明确更好；
- `reproduced`：相近条件多次复现仍优秀；
- `cross_scene_transfer`：迁移到不同场景仍成立。

案例可以立即成为 Golden Case；但技能成熟度不能把 `prompt_approved` 自动当成 `scene_verified`。

## 4.3 Atomic Skill Distillation｜原子技能蒸馏

不学习“整段字符串”，而是逐层检查案例里真正可能有用的变量：

1. 任务定义与剧情目的是否清楚；
2. 参考图 / 资产 / 文本的模态职责是否分工正确；
3. 是否把抽象意图编译成可观察屏幕证据；
4. shot scope、sequence context、reveal、final state 是否干净；
5. 人物目标、潜台词、表演节拍、空间关系是否被正确绑定；
6. 动作是否正向、物理可行、接触与重心清晰；
7. 摄影机、光线、声音、剪辑是否服务剧情而非堆效果词；
8. 时间码是否按需要使用而非强制铺满；
9. prompt constraint budget 是否合理；
10. 是否存在高价值的句法结构、信息顺序、约束作用域、reference binding；
11. 哪些内容其实只是当前场景事实，不应抽成技能；
12. 哪些内容只是模型版本特性，需要 version-bound 标记。

每个候选 lesson 尽量拆成最小知识单元，避免多个同时变化的变量被打包成一个“万能公式”。

## 4.4 Causal Learning｜不把相关误当因果

每个候选 lesson 至少记录：

```yaml
observed_strength:
causal_hypothesis:
primary_variable:
co_changed_variables:
alternative_explanations:
counterfactual:
applicable_context:
non_applicable_context:
failure_boundary:
model_or_tool_dependency:
```

如果一个提示词同时改了 8 件事且结果变好，默认只能说“组合方案有效”，不能假装已经知道第 4 个改动就是主因。

## 4.5 Skill Linkage｜先查重，再新增

新案例优先检查是否强化、限定、冲突或扩展现有技能：

- `SUPPORTS`：强化已有规则；
- `REFINES`：补充适用条件；
- `BOUNDS`：补充失败边界；
- `CONTRADICTS`：与旧经验冲突，转 conflicted；
- `SUPERSEDES`：有充分证据时替代旧规则；
- `NEW_CANDIDATE`：现有系统没有相邻规则时才新建。

禁止每来一个优秀提示词就制造一批同义技能。

## 4.6 Maturity Gate｜案例优秀 ≠ 技能全局稳定

继续使用项目统一成熟度：

```text
candidate
→ scene_verified
→ project_verified
→ general_stable
```

默认规则：

- 用户只认可提示词文本：抽取技能通常 `candidate`；
- 用户明确认可该场景真实生成结果：相关场景 lesson 可按证据进入 `scene_verified`；
- 跨多个不同场景重复成立：才考虑 `project_verified`；
- 跨项目 / 跨模型仍成立且边界清楚：才考虑 `general_stable`。

高影响晋级继续保留人工门。

# 5. STEP 2｜REGISTER：直接登记 Golden Prompt Case

Golden Case 必须保存“原案例 + 证据 + 可检索维度”，而不是只存一段提示词。

最小字段：

```yaml
case_id:
created_at:
source_type: user_supplied_prompt
source_prompt_verbatim: |
  ...
user_verdict:
verdict_scope:
verdict_basis: prompt_only | generated_output | both | comparative
work_item_id:
task_class:
scene_or_shot:
model:
model_version:
generation_mode:
reference_assets:
generation_settings:
output_evidence:
user_named_strengths:
system_observed_strengths:
edcm:
  k0:
  k1:
  k2:
  k3:
extracted_lesson_refs:
related_skill_refs:
applicable_context:
non_applicable_context:
failure_boundaries:
model_or_tool_dependency:
revalidation_triggers:
case_status:
provenance:
```

## 5.1 原文保真

`source_prompt_verbatim` 永远保存用户提供的原提示词，不做：

- 润色；
- 去重；
- 自动补词；
- 语法纠正；
- “更专业”的重写。

系统可以另存 `normalized_summary` / `extracted_lessons`，但不得污染原文证据。

## 5.2 去重与谱系

同一提示词重复提交时优先做 exact / near-duplicate 检查：

- 完全相同：不创建第二个案例，追加新评价或新验证；
- 小改版：建立 `parent_case_id` / `variant_of`；
- revision series 的最终优秀版：保留与 R0/R1/... 的轨迹引用，不把历史差异抹掉。

# 6. Golden Case 的检索与调用

案例库不是每轮全文塞给模型的“大提示词仓库”。调用遵循 Case-Based Reasoning：

```text
RETRIEVE
→ REUSE / ADAPT
→ REVISE / TEST
→ RETAIN
```

当前任务按以下维度检索最相近案例：

1. task_class / symptom tags；
2. 模型与版本；
3. T2V / I2V / multimodal 模式；
4. 场景类型与镜头功能；
5. 人物、资产与空间依赖；
6. 失败症状；
7. 当前导演目标；
8. 已验证 maturity / verdict scope。

默认只取最小必要案例，优先 1–3 个高相似且互补的案例；不得把所有优秀案例统一灌入上下文。

# 7. Golden Set 与 Regression 的分工

Golden Prompt Case 有两种用途，但必须区分：

## 7.1 Demonstration / Precedent

作为历史先例帮助系统理解“这个项目里用户认为什么是优秀”。

## 7.2 Evaluation Reference

作为回归评价参照，检查新系统是否破坏已有能力。

**同一个案例如果已经直接作为 few-shot / retrieval 输入，就不能再把它作为唯一的独立泛化证明。**

因此每个高价值 Golden Case 后续应尽量产生：

- `golden_reference`：原案例；
- `sibling_transfer_case`：相同技能、不同内容；
- `contrast_case`：相似表面但不应套用该技能；
- `holdout_case`：不直接进入生成上下文，用于检验迁移。

这用于降低“背答案”“只会模仿模板”和 eval contamination。

# 8. Human Verdict 与自动 Grader

用户作为本项目领域主导者，对“当前案例是否是优秀参考案例”拥有最高判断权。

自动 grader 只能辅助，不得覆盖用户判断。自动评估优先承担：

- 指令遵循；
- 人物身份 / 资产 / 连续性；
- shot scope；
- 空间关系；
- 身体力学；
- 时间稳定；
- 画面可观察性；
- prompt complexity；
- 回归差异定位。

开放式审美、导演品味、细微表演质量等仍以用户真实评价 + 项目验收为主。

若自动 grader 没有可靠 reference 或未校准，应降低置信度，不得用“模型自己说自己优秀”推动 maturity 晋级。

# 9. Model / Tool Version Cycle

优秀提示词可能强依赖模型版本。案例登记时尽量记录：

- provider；
- model family；
- exact model version / snapshot（能确认时）；
- generation mode；
- 关键参数；
- reference interface；
- 日期。

以下事件触发 `needs_revalidation`：

- Seedance / Seedream / ChatGPT / 其他生成模型大版本变化；
- 官方提示规范发生实质变化；
- 同提示词在新版本出现明显漂移；
- 旧案例长期未复验且依赖版本特性；
- 关键 reference / negative prompt / multimodal 接口变化。

稳定导演原则与模型语法分开管理，避免“模型换代 → 整个导演系统一起失忆”。

# 10. Experience Replay 但不无脑 Replay

优秀案例库承担项目的 experience replay / rehearsal 功能，帮助系统防止旧经验被新经验覆盖。

但 replay 本身不是越多越好：

- 只按任务相关性回放；
- 保留不同类型、不同失败边界的案例多样性；
- 冲突案例不删除，标 `conflicted` 并按条件路由；
- 新案例不能因为更新而静默抹掉旧案例成立过的历史条件；
- 若案例量变大，采用代表性 selection，而不是全量注入。

# 11. Prompt Cargo-Cult 防护

每次学习优秀案例都执行反机械模仿扫描：

- 这句话是因果变量，还是只是漂亮措辞？
- 这个结构对当前模型有效，还是对所有模型都有效？
- 这个细节来自场景事实，还是通用导演方法？
- 去掉该元素，结果是否仍可能成立？
- 是否存在更简单的表达也能达到同一效果？
- 相反场景里套用它会不会更糟？

目标不是让系统越来越会“复制优秀提示词”，而是越来越会**知道为什么这个案例优秀、什么时候该参考、什么时候绝对不该照搬**。

# 12. 外部知识映射

本协议吸收但不机械复制以下知识线，详细证据与版本见 `09_资料证据/优秀提示词案例学习证据索引.md`：

- OpenAI contextual evals：Specify → Measure → Improve；golden set 作为领域专家对“great”判断的 living authoritative reference；
- OpenAI Evals / Graders：数据集 + 多种 grader + 回归；
- OpenAI 内部 Data Agent：人工 authored golden answer + 持续 unit-test 式 eval；
- OpenAI model version guidance：模型 snapshot 行为会变化，应用应 pin version + eval；
- Case-Based Reasoning：Retrieve → Reuse → Revise → Retain；
- DSPy：把 demonstrations、metrics 与 pipeline 优化分离，避免只靠手工 prompt string；
- Reflexion：把自然语言反馈写入 episodic memory，在不改模型权重的情况下改善后续决策；
- Continual Learning / Experience Replay：保留代表性历史经验缓解遗忘，同时警惕 replay 选择不当产生负迁移；
- adaptive test reuse / contamination：训练或检索使用过的案例不能独立证明泛化；
- LLM-as-a-Judge calibration：开放式任务无 reference 时自动 judge 可能偏宽松，必须校准并保留人类专家判断。

# 13. 写回事务

每次 Golden Prompt Case 强触发，内部事务：

```text
FETCH PROJECT_INDEX
→ READ GPCL + feedback engine + maturity + relevant domain canonical
→ STEP 1 LEARN
   → EDCM scan
   → atomic lessons
   → linkage / conflict
   → maturity
   → targeted eval / regression candidate
   → write lesson to unique target canonical or mark pending
→ STEP 2 REGISTER
   → preserve source_prompt_verbatim
   → write/update golden_prompt_cases.yaml
→ FETCH AGAIN
→ VERIFY case + lesson refs + statuses
→ report only verified writes
```

若其中一路写回失败：

- 不得说“全部录入成功”；
- 明确报告 `case_registered / learning_pending` 或 `learning_written / case_pending`；
- 下一项目回合优先检查 pending canonical write。

# 14. 用户最终体验

用户以后只需要正常说：

> “这个提示词是优秀案例，录进去。”

系统应自动完成：

```text
① 学习它
② 原文入 Golden Case
```

用户无需管理 schema、case_id、maturity、eval、回归、GitHub commit、版本依赖或知识映射。
